# Deploying RoleTailor

This runbook covers the cloud deployment: hosting, file storage, secrets, database migrations, and CI/CD. Local development stays on `docker compose` (see the README).

## Why Fly.io

| Need | Fly.io answer |
|---|---|
| Run the existing images as they are (the worker needs LibreOffice) | Deploys any Dockerfile. No buildpack changes. |
| API and Celery worker from one image | One app with two process groups (`app` and `worker`) that share the image, secrets and release. |
| Migrations at deploy time | `release_command` runs `python db/migrate.py` once per release, before any new machine starts. A failed migration aborts the deploy, and the old version keeps serving. |
| Postgres 16 with pgvector and RLS | Fly Managed Postgres, which ships pgvector. The app keeps its two-role design (`rt_owner` runs migrations, `rt_app` is bound by RLS). |
| S3-compatible file storage | Tigris, through `RT_S3_ENDPOINT_URL`. No code changes are needed. |
| Secrets | `fly secrets`, which are encrypted at rest and injected as environment variables. CI holds only a deploy token. |
| Cost | About $60 a month for production and $15 for staging (see below). |

**Portability.** Nothing in the application depends on Fly. Every setting is an `RT_` environment variable, storage is plain S3, and the database is plain Postgres. To move providers, keep the images and the env files and replace only `deploy/fly/`:

- **Render:** a `render.yaml` with a web service (API), a background worker, a web service (Next.js), Render Postgres, Render Key Value, `preDeployCommand: python db/migrate.py`, and S3 or Cloudflare R2 for files.
- **AWS:** ECS Fargate services for the API, worker and web, RDS Postgres 16, ElastiCache, and S3. Run migrations as a one-off ECS task before the service update. Expect about $100 or more a month, mostly for the load balancer and NAT.

## Topology

```
                     https://app.<domain>                       https://api.<domain>
 browser ──────────► roletailor-web (Next.js) ──── /v1 ───────► roletailor-api  [app]    uvicorn :8000
                                                    Stripe ───► (public)        [worker] celery
                                                                      │   │   │
                     private network (6PN) ◄──────────────────────────┘   │   └──► Tigris bucket (files)
                     roletailor-redis (broker, rate limits, LLM cache)    └──────► Fly Managed Postgres
```

Staging uses the same names with a `-staging` suffix. Redis is never exposed publicly. The API is public because share links and Stripe webhooks call it directly.

## Files

| Path | Purpose |
|---|---|
| `deploy/fly/api.toml` | API and worker app: process groups, release command, health checks, VM sizes |
| `deploy/fly/web.toml` | Next.js app |
| `deploy/fly/redis.toml` | Private Redis with a persistent volume |
| `deploy/fly/env/<env>.{api,web}.env` | Settings for each environment that are not secret (URLs, bucket, `RT_ENVIRONMENT`). These files are committed. |
| `deploy/fly/bootstrap.sh` | One-time setup for an environment: creates the apps, volume, bucket and secrets |
| `deploy/fly/deploy.sh` | Deploys an environment. CI uses it, and you can run it by hand. |
| `db/bootstrap/managed_roles.sql` | One-time creation of `rt_owner` and `rt_app` on the managed cluster |
| `.github/workflows/ci.yml` | Lint, tests, offline eval, frontend build and image builds on every PR |
| `.github/workflows/deploy.yml` | Deploys staging automatically after CI passes on `main`. Production deploys are manual and need approval. |

## Secrets

Secrets live only in Fly, and in GitHub as a deploy token. They are never committed.

| Secret | App | Source |
|---|---|---|
| `RT_DATABASE_URL` | api | Pooled connection as `rt_app`, using the `postgresql+psycopg://` scheme |
| `RT_MIGRATION_DATABASE_URL` | api | **Direct** (unpooled) connection as `rt_owner`. The migration runner holds a session advisory lock, which transaction pooling would break. |
| `RT_REDIS_URL` | api | Set by `bootstrap.sh` (`redis://default:<pw>@roletailor-redis.internal:6379/0`) |
| `REDIS_PASSWORD` | redis | Generated by `bootstrap.sh` |
| `RT_PROXY_SHARED_SECRET` / `API_PROXY_SECRET` | api / web | One value, generated by `bootstrap.sh`, set on both apps. The web app relays each browser's address to the API (`X-RT-Client-IP`) and the API believes it only with this secret, so rate limits are per visitor. `X-Forwarded-For` is never trusted. Outside dev, the API refuses to start without it. |
| `RT_METRICS_TOKEN` | api | Optional. When set, `GET /metrics` requires `Authorization: Bearer <token>`. Without it, `/metrics` answers only requests that did not come through the public edge. |
| `RT_SECRET_KEY` | api | Generated by `bootstrap.sh` (`openssl rand -hex 32`). Outside dev, the app refuses to start if this is the default or shorter than 32 characters. |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`, `BUCKET_NAME` | api | Set by `fly storage create`. boto3 reads the `AWS_*` values automatically. |
| `ANTHROPIC_API_KEY`, `DEEPSEEK_API_KEY` | api | Your provider consoles |
| `RT_STRIPE_SECRET_KEY`, `RT_STRIPE_WEBHOOK_SECRET`, `RT_STRIPE_SUBSCRIPTION_PRICE_ID` | api | Stripe dashboard (use test mode for staging) |
| `FLY_API_TOKEN` | GitHub environments `staging` and `prod` | `fly tokens create deploy -a roletailor-api` (one token for each app set, or an org deploy token) |

To rotate a secret, run `fly secrets set NAME=value -a <app>`. This restarts the machines with the new value. For the database passwords, run `ALTER ROLE ... PASSWORD` first, then update both URLs.

## First-time setup (one environment)

These steps need your Fly account and credentials. Start with staging.

1. **Create the accounts.** Create a Fly.io account with billing, then install `flyctl` and run `fly auth login`. Have your Anthropic, DeepSeek and Stripe keys ready.
2. **Choose domains.** Edit `deploy/fly/env/<env>.api.env` and `<env>.web.env` and replace the `roletailor.example` placeholders. If the bucket name is taken, change `RT_S3_BUCKET` as well.
3. **Create the database.**
   ```bash
   fly mpg create --name roletailor-staging --region iad      # choose the Developer plan for staging and Basic for prod
   fly mpg connect                                            # or use the admin URL the dashboard shows
   psql "$ADMIN_URL" -v owner_password="$(openssl rand -hex 24)" -v app_password="$(openssl rand -hex 24)" \
        -f db/bootstrap/managed_roles.sql
   ```
   Keep both passwords in your password manager. If the cluster admin cannot create roles, create users named `rt_owner` and `rt_app` with `fly mpg users` instead. `rt_app` must not be a superuser, own the database, or have BYPASSRLS.
4. **Run the bootstrap script.** `deploy/fly/bootstrap.sh staging` creates the three apps and the Redis volume, creates the Tigris bucket, generates `REDIS_PASSWORD` and `RT_SECRET_KEY`, and prompts for the provider and Stripe keys without echoing them.
5. **Set the database URLs.**
   ```bash
   fly secrets set --stage -a roletailor-api-staging \
     RT_DATABASE_URL='postgresql+psycopg://rt_app:<pw>@<pooled-host>:5432/roletailor' \
     RT_MIGRATION_DATABASE_URL='postgresql://rt_owner:<pw>@<direct-host>:5432/roletailor'
   ```
6. **Deploy.** Run `deploy/fly/deploy.sh staging redis` once, then `deploy/fly/deploy.sh staging`. The API release runs the migrations, and the web app deploys after it.
7. **Add DNS and certificates.** Run `fly certs add api-staging.<domain> -a roletailor-api-staging` and do the same for the web app, then add the DNS records Fly prints.
8. **Point Stripe at the API.** Add a webhook endpoint at `https://api-staging.<domain>/v1/billing/webhook` and put its signing secret in `RT_STRIPE_WEBHOOK_SECRET`.
9. **Wire up CI.** In GitHub, go to Settings, then Environments, and create `staging` and `prod`. Give each a `FLY_API_TOKEN` secret and an `API_URL` variable (for example `https://api-staging.<domain>`). Add yourself as a required reviewer on `prod`.
10. **Smoke test.** `curl https://api-staging.<domain>/readyz` should return `ready`. Then register, upload a resume and run one tailoring.

Repeat for `prod` with the Basic Postgres plan and live Stripe keys.

## Everyday deploys

- **Staging:** every merge to `main` runs CI. If CI passes, `deploy.yml` deploys staging and checks `/readyz`.
- **Production:** go to Actions, then Deploy, then Run workflow, and choose environment `prod`. After a reviewer approves, the commit already proven on staging is deployed.
- **By hand:** `FLY_API_TOKEN=... deploy/fly/deploy.sh prod api`.

## Migrations

- Migrations are forward only. Each `db/migrations/NNN_*.sql` file manages its own transaction. They are recorded in `public.schema_migrations` and serialised with an advisory lock.
- Old and new code run side by side during a rolling deploy, so keep migrations backwards compatible: add columns before the code that uses them ships, and drop them in a later release.
- If a migration fails, the release stops before any machine is replaced. Fix the migration in a new commit and deploy again.

## Rollback

- **Code:** run `fly releases -a roletailor-api` to find the previous image, then `fly deploy -a roletailor-api -c deploy/fly/api.toml --image <previous-image>` (and the same for the web app). This does not reverse migrations, which is why they must stay backwards compatible.
- **Database:** `fly mpg restore` gives point-in-time recovery on Basic and above. The Developer plan has daily snapshots only.
- **Files:** Tigris buckets have no object versioning unless snapshots are enabled. The app stores a new key for each generated file and never overwrites one, so a code rollback loses no files.

Model spend is separate, at about $0.04 per generation (see `docs/architecture.md`).

## Monitoring hooks (roadmap item 8)

The API serves `/metrics` and the worker serves Prometheus metrics on port 9101. Fly scrapes the port declared in `[metrics]` into its managed Prometheus, and Grafana is available at fly-metrics.net. Per-call cost, latency and fabrication data live in the `ai_metrics` and `validation_results` tables. The dashboards and alerts are a separate roadmap item.
